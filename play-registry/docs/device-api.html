DeviceAPI 参考

注入到每个玩法页面的统一桥接 API · PC 与 Android 接口完全一致

每个玩法页面通过 <script src="/bridge-api/device-api-bridge.js"></script> 引入桥接脚本，它创建全局 window.DeviceAPI（WebSocket 自动连回脚本来源的后端，与页面自身端口无关——所以不要用别处的脚本副本，务必从面板后端加载）。所有设备交互都通过它完成——不要自己开 WebSocket。通道就绪前调用会失败，请先 await DeviceAPI.ready。

window.DeviceAPI = {
  device(logicalId),       // 获取设备代理
  getDevices(),            // 列出已连接设备及能力
  getDeviceMap(),          // 当前会话 logicalId → physicalId[]
  log(level, message, meta),
  onSystemLog(cb), offSystemLog(cb),
  params,                  // 用户启动时配置的参数
  deviceMap,               // {logicalId: physicalId[]} 恒为数组
  ready,                   // Promise，Bridge 就绪后 resolve
};

device(id) — 设备代理

通过逻辑设备 id 拿到代理对象，调用其能力方法。id 来自你 manifest 里 devices[].id。

方法说明
invoke(capability, action, params)调用能力方法（走 Capability 路由，有校验、有映射）。推荐入口。
writeProps(props)直接写属性字典（跳过能力层）。调试或能力未覆盖时用。
sendMessage(msg)直接发消息给设备（跳过能力层）。
on(capability, event, cb)监听能力事件（由能力的 events 定义）。
off(capability, event, cb)取消能力事件监听。
onValue(capability, cb)监听能力标量值变化，回调参数为 (value, oldValue, physicalId)。
offValue(capability, cb)取消能力值监听。
onProperty(property, cb)低层：监听底层属性变化。
offProperty(property, cb)低层：取消属性监听。
onMessage(cb)低层：监听设备原始消息。
offMessage(cb)低层：取消原始消息监听。
async read(property)读属性缓存值（异步，返回数组，顺序同 deviceMap 物理 ID）。
async readValue(capability)按设备类型解析能力当前值（异步，返回数组）。
isMapped()该逻辑设备是否已映射到物理设备（bool）。

关键语义

invoke vs writeProps

invoke 走 Capability 路由，有校验、有逻辑→物理映射，是推荐入口。writeProps 直接把属性字典发给设备，跳过能力层，适合调试或能力体系未覆盖的场景。sendMessage 直接给设备发原始消息。

deviceMap 恒为数组

deviceMap 和 getDeviceMap() 的值固定是 physicalId[]。一个逻辑设备可对应多个物理设备，未映射时为空数组 []，不会出现单值或 undefined。device(id).isMapped() 等价于「该数组非空」。

多物理设备语义

  • 下行广播：invoke / writeProps / sendMessage 对所有映射的物理设备执行同一操作。
  • 上行逐设备触发：on(capability, event) 回调里 data 含触发源物理设备 ID（data.physicalId）及该设备属性，每个物理设备独立触发、不合并。

read 返回数组

read(property) 是异步方法，从宿主属性缓存读取（不发起设备查询），返回数组——顺序与 deviceMap 中物理 ID 顺序一致。例如映射了两个传感器：[72] 或 [72, 68]。

能力值三入口一致

readValue、onValue 和启动时的首次 readValue 使用同一设备类型解析规则。底层属性变化但解析后的标量值不变时，onValue 不会重复触发。read / onProperty 仍作为兼容和调试用低层接口保留。

ready

桥接脚本保证在 DOM 可用前注入，但 WebSocket 连接需要时间。所有设备操作之前必须 await DeviceAPI.ready。

设备离线

invoke / writeProps / sendMessage 调用时若设备离线，宿主不抛错，而是通过 systemLog 推一条 warn 日志（「设备 X 可能离线」）。用 onSystemLog 监听。

使用示例

// 1. 等通道就绪
await DeviceAPI.ready;

// 2. 通过能力调用（推荐，有校验）
DeviceAPI.device('motor').invoke('strength', 'set', { value: 128 });
DeviceAPI.device('punish').invoke('shock', 'start', { voltage: 30 });

// 3. 可选设备先判断再调
if (DeviceAPI.device('punish').isMapped()) {
  DeviceAPI.device('punish').invoke('shock', 'start', { voltage: 30 });
}

// 4. 监听能力事件
DeviceAPI.device('sensor').on('sphincterPressure', 'pressureChange', (data) => {
  const val = data.props.pressure;
  if (val > threshold) {
    DeviceAPI.device('punish').invoke('shock', 'start', { voltage: 30 });
  }
});

// 5. 读当前能力值，并监听后续变化
const pressures = await DeviceAPI.device('sensor').readValue('sphincterPressure'); // [72]
DeviceAPI.device('sensor').onValue('sphincterPressure', (value, oldValue, physicalId) => {
  console.log(physicalId, oldValue, '->', value);
});

// 6. 回传日志到宿主统一聚合
DeviceAPI.log('info', '进入惩罚阶段', { count: 3 });

// 7. 监听系统日志（设备离线警告等）
DeviceAPI.onSystemLog((entry) => {
  if (entry.level === 'warn') console.warn(entry.message, entry.meta);
});

// 8. 低层接口（调试用）
DeviceAPI.device('sensor').onProperty('pressure', (val, old) => {
  console.log('pressure:', old, '→', val);
});
DeviceAPI.device('qtz').onMessage((msg) => console.log('raw:', msg));

能力事件 data 结构

on(capability, event, cb) 回调的 data 含：

字段说明
data.props设备属性快照（dict）
data.changed本次变化的属性 key
data.msg触发的原始消息对象（消息类事件才有）
data.physicalId触发源物理设备 ID（多物理设备时区分来源）

运行模型：游戏自驱动

玩法逻辑完全在页面 JS 内自驱动。计时、阶段切换、强度递增、惩罚检测等节奏由页面自己的 setInterval / requestAnimationFrame 维护。宿主不提供 loop() 回调——游戏即网页，状态由页面自己持有。

⚠️

页面定时器在后台标签/息屏时可能被节流，因此设备安全不能依赖页面逻辑。关键安全（停止电击、强度归零）由宿主 close 兜底强制保证：游戏主动结束、连接断开超 180s、下一个玩法启动时，宿主对该会话所有映射设备强制调用 close，页面崩溃也能保证设备停止。

# 多游戏配音问题审查与修复计划

## 文档状态

- 日期：2026-07-21
- 状态：实施中
- 涉及游戏：`drink-pee-unlock`、`pressure-edging`、`pressure-edging-v2`
- 审查基准：`HEAD` 与当前工作区未提交修改

## 结论

当前配音修改完成以下修复后方可提交或发布：

1. `pee` 模式的核心台词与“重量上升”的玩法目标相反，且原文案过长、包含敏感表达。
2. 三个游戏都允许多个 `Audio` 实例并行播放，部分默认流程会稳定复现叠播。
3. 旧版寸止的开局恢复提示和全局 key 去重与真实状态迁移不一致。

CUNZHI01 修改保留在工作区，本轮不修改、不提交；配音随机数对随机振动的统计分布没有影响，本轮接受现状。统一 common JS 另见 [游戏 common JS 运行时计划](2026-07-21-game-common-js-runtime.md)，本轮不实施。

修复时必须保持以下边界：

- 配音失败、禁用或被浏览器拦截时，游戏状态机与设备输出必须照常运行。
- 不得为了容纳较长语音而延长电击时间、冷却时间或游戏时长。
- CUNZHI01 接入和结束后回调保护应与配音拆成独立变更，分别评审和测试。
- 两个 `pressure-edging` 游戏原有的状态迁移、强度计算、电击和锁控制不得因配音修复而改变。

## 审查证据

- 三个游戏目录共有 38 个 MP3 文件，均可完整解码；代码引用的音频没有缺失。
- 旧版和升级版寸止游戏的 7 个同名音频与生成目录逐字节一致。
- 音频时长约 3.95 至 14.64 秒，明显长于部分 200ms 至 2 秒的状态迁移窗口。
- `drink-pee-unlock` 定向测试 9/9 通过；后端全量测试 120 项通过、1 项跳过。
- 现有测试通过只能证明既有断言未回归，不能证明没有叠播或台词语义正确。

## 1. pee 模式台词方向错误

### 现象

以下台词都把 pee 模式描述为“忍住”：

- `start_pee`：“要好好忍住”
- `encourage_pee`：“忍住了吗……再坚持一下”
- `unlock_pee`：“你坚持住了，目标达成”

### 原因

台词把“憋尿解锁”的名称理解成持续憋尿，但实际状态机以电子秤重量增加作为进度，并在重量长时间不增加时触发“排泄惩罚”。原玩法文档也明确规定“饮水为下降、尿量为上升”。

因此，这不是风格问题，而是任务方向错误：用户按语音继续忍住，反而不会产生游戏要求的尿量进度。

### 推荐修复

重新编写并生成三条短音频，只描述可观察目标，不使用“忍住”“坚持住”“排尿”“尿量”等表达。确定文案：

| key | 推荐文案 |
| --- | --- |
| `start_pee` | “准备好了吗？让重量持续增加，我们开始吧。” |
| `encourage_pee` | “继续保持重量上升，不要停哦。” |
| `unlock_pee` | “目标已达成，解锁成功。” |

生成后应由人工完整试听，确认内容、断句和文件 key 一致。

### 验收

- 代码进入 pee 模式时只引用 pee 文案。
- 三条音频不包含敏感词，也不再表达“继续忍住”。
- 文案与 `progress = weight - initialWeight` 及停滞惩罚语义一致。

## 2. 多音频并行播放

### 现象

当前每次播报都会执行 `new Audio(...)`，但没有保存、暂停或释放上一条音频。已确认的稳定场景包括：

- `drink-pee-unlock` 默认电击持续 2 秒，而惩罚音长约 6 至 7 秒；进入冷却时会在惩罚音尚未结束时播放 `cooldown_start`。
- `pressure-edging` 的开场音约 14.64 秒，首次 200ms 循环通常又会播放 `edging_delay`。
- 里程碑、随机鼓励、姿态提醒和结束播报也可能在前一条音频仍播放时触发。

旧的 `speechSynthesis` 实现会先 `cancel()`，新实现丢失了这一互斥语义。

### 原因

播放函数只负责“创建并播放”，没有把语音播放建模成有状态资源，也没有定义不同事件之间的优先级、抢占和跳过规则。

### 推荐修复

本轮先在三个游戏内实现相同的单实例 `VoicePlayer` 行为契约；暂不抽取共享脚本，后续由 common JS 计划统一承载：

```js
const voice = createVoicePlayer({ basePath: 'voices', enabled: true });

voice.play(key, { priority: 'critical' });
voice.stop();
voice.setEnabled(false);
voice.isPlaying();
```

播放器必须满足：

1. 任意时刻最多一个活动 `Audio`。
2. `play()` 决定抢占或跳过时，先停止旧音频，再替换引用。
3. 监听 `ended`、`error`，结束后释放引用；加载失败要记录包含 key 和 URL 的日志。
4. 自动播放被拒绝时最多保留一条“当前仍有效”的待播事件，不能积压过期状态。
5. 禁用语音时立即停止当前音频并清空待播事件。

建议的事件策略：

| 事件 | 优先级 | 策略 |
| --- | --- | --- |
| 结束、惩罚、过载 | critical | 立即抢占当前语音 |
| 冷却、平静、中期、起飞 | state | 抢占提示类语音；只在状态仍有效时播放 |
| 开场 | intro | 普通阶段和提示不得抢占；只保留最新且仍有效的阶段事件 |
| 进度、鼓励、姿态提醒 | info | 有语音正在播放时直接跳过，不排队 |

开场包含“可以自行调整参数”等重要信息，应尽量完整播放；惩罚、过载和结束等 critical 事件仍可立即中断开场。播放器不得暂停游戏计时、传感器监控或设备控制。

此外应缩短惩罚台词，使其能在默认 2 秒惩罚窗口内表达核心信息。不得通过增加 `shockDuration` 解决音频过长问题。

### 验收

- 测试期间活动音频实例数始终不超过 1。
- 惩罚转冷却、开场转阶段、提醒转结束都没有叠播。
- 没有 critical 事件时，开场信息可以完整播放。
- 音频播放失败不会中断状态机循环或设备安全收尾。
- `voiceEnabled=false` 时不创建或补播任何音频。

## 3. CUNZHI01 改变原玩法（本轮暂缓）

### 现象

`drink-pee-unlock` 同时新增了：

- `cunzhi` 设备角色和 `tiptoePressure` 能力要求。
- 压力阈值、防抖参数和界面指标。
- `pressure1` 属性订阅与上报频率调整。
- 压力超阈值后的新惩罚、电击路径。

映射该设备后，压力超过默认阈值 100 持续 300ms 会触发原版不存在的电击。

### 原因

配音开发过程中混入了另一个功能需求。该功能不仅扩大修改面，还直接影响惩罚设备，无法作为配音实现细节接受。

### 本轮决策

1. 保留当前工作区中的 CUNZHI 代码、参数、UI、音频和测试，不在本轮修改。
2. 本轮提交通过精确暂存排除所有 CUNZHI 修改。
3. 后续继续核对初始压力读取、防抖精度、QTZ 与 CUNZHI 同时映射语义，再决定独立提交。
4. 能力读取终态仍按 [QTZ 踮脚压力接入计划](2026-07-20-qtz-tiptoe-capability-value-contract.md) 处理。

### 验收

- 纯配音 commit 的设备映射、状态转移和 DeviceAPI 调用轨迹与 `HEAD` 一致。
- 本轮 commit 不包含 CUNZHI 功能。
- CUNZHI 工作区修改没有因配音修复被删除或覆盖。

## 4. 旧版寸止开局播放错误阶段提示

### 现象

`pressure-edging` 启动时 `currentPressure` 为 0，`isInDelayPeriod` 为 false。第一次循环会进入低压分支并播放 `edging_delay`：“先缓一缓，给你几秒钟冷静一下”。此时用户尚未经历过载或寸止，台词与当前阶段不符。

### 原因

原状态机用同一个低压延迟分支完成开局初始化和过载后的恢复，但配音把这个内部实现分支直接解释成“过载后的冷静期”。内部条件相同，不代表用户语义相同。

### 推荐修复

增加独立的语音阶段跟踪，不修改原强度计算和延迟计时：

- 只有发生过 `pressure >= criticalPressure`，随后从超压回落时，才播放 `edging_delay`。
- 初始低压进入现有延迟逻辑时不播恢复台词。
- 若产品需要开局低压提示，应新增准确文案，例如“正在等待压力进入训练区间”，不要复用恢复台词。

### 验收

- 开局压力为 0 时只播放开场音，不播放 `edging_delay`。
- 第一次真实超压后回落时播放一次 `edging_delay`。
- 强度曲线、延迟起点和 DeviceAPI 调用与修复前一致。

## 5. 全局 key 去重压掉合法播报

### 现象

旧版寸止已经用 `_inMidBand` 做上升沿检测，但 `playVoice()` 又用 `_lastVoiceKey` 永久抑制连续相同 key。用户离开中期区间后再次进入，如果期间没有其他语音，第二次 `edging_middle` 不会播放，与“每次跨入都播”的注释不一致。

### 原因

“防止同一循环重复播放”和“永远不允许连续两次相同事件”被实现成了同一个全局规则。状态边沿已经负责前一种需求，全局 key 去重反而删除了后续合法事件。

### 推荐修复

- 保留状态机或 `_inMidBand` 的边沿检测。
- 删除永久 `_lastVoiceKey` 去重。
- 播放器只在“相同 key 当前仍在播放”或极短防抖窗口内去重，例如 300 至 500ms。
- `pressure-edging-v2` 继续以明确的状态迁移作为播报边界，不在播放器里推断状态。

### 验收

- 中期区间内持续抖动不会每个循环重复播报。
- 完整离开中期后再次进入，可以再次播报。
- 同一状态未迁移时不会重复创建音频。

## 6. 配音随机数影响游戏随机序列

### 现象

`drink-pee-unlock` 原本使用 `Math.random()` 判断随机振动。新增鼓励和提醒逻辑在每次循环中继续调用 `Math.random()`，虽然振动的统计概率不变，但后续使用到的随机值发生变化，具体振动触发时点会与原版不同。

随机等待阈值还在每次循环重新抽取，所以注释所说的“60 至 120 秒随机一次”并不是先抽取一个固定等待时间，实际分布会偏向区间前部。

### 原因

游戏随机行为和配音调度共用全局随机源，而且随机截止时间没有在一次播报后固定下来。

### 本轮决策

本轮不修改。新增随机调用会改变单次运行的具体随机序列，但每秒随机振动的统计概率不变；当前没有固定种子、回放或严格可复现契约，因此接受这一差异。

### 验收

- 随机振动的配置概率和判断位置不变。
- 不新增为保持随机序列而设计的额外代码。

## 7. 未使用音频和重复产物

### 现象

- `warn_drink_stall.mp3`、`warn_pee_stall.mp3`、`warn_pressure.mp3` 没有任何代码引用。
- 旧版 `pressure-edging` 没有起飞阶段，却携带 `edging_takeoff.mp3`。
- `tools/cosyvoice/output_voices` 完整重复游戏目录中的音频，当前约 3.45MB。

### 原因

生成清单先于触发设计完成，生成产物目录也没有和最终运行资源区分。

### 推荐修复

- 当前版本删除三条未使用警告音；若确实需要预警，先单独设计预警状态，不能为了播放警告而延迟已有即时惩罚。
- 从旧版寸止目录删除未使用的 `edging_takeoff.mp3`。
- 将 `tools/cosyvoice/output_voices/` 视为可再生产物并加入 `.gitignore`，仓库只保留实际游戏引用的最终资源。
- 调整 `.gitignore`，允许提交 `tools/cosyvoice/.env.example`，但继续忽略真实 `.env`。
- 生成脚本完成后输出“引用、缺失、未使用”清单，缺失时返回非零退出码。

### 验收

- 每个游戏目录满足“代码引用集合 = MP3 文件集合”。
- Git 不再显示 `output_voices` 中间产物。
- 生成工具不包含密钥，且新环境能根据示例配置运行。

## 8. 播放器代码重复（后续 common JS）

### 现象

三个 `game.js` 各自复制了约 30 行 `Audio` 创建、自动播放重试和 key 去重逻辑。当前实现已经出现差异：喝水游戏和寸止游戏的重试、去重行为并不一致。

### 原因

缺少明确的语音播放契约，功能以页面内代码复制的方式接入。

### 本轮决策

本轮不修改运行时加载方式。先让三个游戏采用同一行为契约，后续按 [游戏 common JS 运行时计划](2026-07-21-game-common-js-runtime.md) 提供类似 `DeviceAPI` 的共享脚本，并迁移本轮播放器实现。

### 验收

- 独立计划固定 common JS 的 interface、加载 seam、版本和测试方式。
- 本轮不新增 `/bridge-api/game-common.js`，也不改变现有游戏加载链路。

## 9. 测试覆盖不足

### 现象

现有 `drink-pee-unlock` 测试只记录 Audio URL，`play()` 永远成功；两个寸止游戏没有覆盖配音状态切换的自动化测试。测试无法发现叠播、开局错误提示、自动播放拒绝或重复中期被抑制。

### 原因

测试替身只验证“调用了某个文件名”，没有模拟音频生命周期；状态机测试也没有把配音视为可观察输出。

### 推荐修复

#### 播放器单元测试

- 同时最多一个活动音频。
- 高优先级抢占、低优先级忙时跳过。
- `ended`、`error`、`play()` reject 后正确清理。
- 首次用户手势只补播仍有效的最新事件。
- 禁用会停止当前音频并阻止后续播放。

#### 游戏状态测试

- drink：drink/pee 开场、停滞惩罚、冷却、达标、超时、手动结束。
- pressure v1：开局低压不播 delay、首次跨入 mid、离开后再次跨入、超压和回落。
- pressure v2：CALM/MIDDLE/EDGING/DELAY、结束前起飞和结束。
- 所有场景同时断言原状态、设备调用和语音事件，防止配音钩子改变玩法。

#### 资源契约测试

- 扫描代码或维护显式 voice manifest，断言引用文件存在。
- 断言没有未引用 MP3。
- 使用 `ffprobe` 或等价解码检查验证格式、时长和可解码性。

### 验收

- 新测试能在当前有问题的实现上稳定失败，在修复后通过。
- 两个寸止游戏不再是配音零测试状态。
- 后端全量测试无新增 open handle 或定时器泄漏。

## 10. 其他非配音变化

### 结束后忽略称重回调

`onWeightSample()` 新增 `if (!rt.running) return`，用于避免结束后再次更新状态或播报。方向合理，但它仍是原行为变化，应拆成独立 commit，并补充“结束后称重事件不改变进度、不重复结束”的测试。

### 文档空格

`git diff --check` 当前还会报告 `AGENTS.md` 的行尾空格。它与配音无关，提交前应单独清理，避免混入功能 commit。

## 推荐实施顺序与提交边界

1. `fix(games): correct pee-mode voice copy`
   - 只改台词源和对应 3 个 MP3。
2. `fix(games): serialize game voice playback`
   - 实现统一播放器、优先级和自动播放恢复。
3. `fix(games): align pressure voice triggers with state transitions`
   - 修复开局 delay 和重复 mid 触发。
4. `test(games): cover voice lifecycle and state cues`
   - 增加三款游戏的播放器、状态和资源测试。
5. `chore(games): remove unused generated voice assets`
   - 清理未引用音频和生成目录。
6. CUNZHI01 与结束后称重保护保持在工作区，不进入上述配音提交。
7. common JS 按独立计划后续实施；随机数项关闭，不安排实现。

每个提交都应只暂存对应文件，避免把当前工作区其他未提交修改一并带入。

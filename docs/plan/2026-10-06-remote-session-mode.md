# 远程会话模式（客户端级远控）方案

> 状态：方案待审阅（2026-10-06）
> 术语：**被控端** = 设备所在、被远程操作的客户端；**主控端** = 发起远程操作的客户端。
> 承接：[2026-09-23-remote-game-client-control.md](2026-09-23-remote-game-client-control.md) §7「客户端级远控」，本文把它细化为可实施方案；游戏级远控（HostRuntime）沿用该文。
> 现状基础：远程设备投影、远程游戏两条链路已在生产 room API + EMQX 上回归通过（见 `docs/test/remote-control-e2e-2026-10-06.md`）。

## 0. 已确认决定（用户 2026-10-06）

1. 远程状态下开放：设备控制、游戏（PC 端无独立「场景」功能，见 §3）；设置、插件、账号只读或禁用。
2. 被控端要能看到主控端在做什么（操作记录），并可随时一键踢出。
3. 先做 PC↔PC；远期增加手机↔PC 互控 → **线上协议不得绑定 PC 后端的 REST 路径**。
4. 游戏走「逻辑跟着设备走」：要快速响应设备的游戏改为逻辑与画面分离，逻辑在被控端跑，两端都有画面；其余游戏在主控端跑，经远程设备映射驱动（§4.5）。
5. 分离式游戏的逻辑文件不做运行隔离，安全靠上架审核。

## 1. 目标体验

主控端连上被控端后，整个客户端切换到「被控端的上下文」：设备列表、设备详情、手动控制、游戏库、游戏配置、游戏运行页显示的都是被控端的设备和状态，操作方式与操作本机一致。断开后回到本机。

不是屏幕推流：主控端用自己的界面渲染，只有「请求 + 状态」走网络，延迟是一次 MQTT 往返（实测同城约 50–150ms）。

## 3. 功能范围

| 区域 | 远程状态 | 说明 |
|---|---|---|
| 设备列表 / 详情 / 昵称 / 控制连接切换 | 开放 | 读被控端的真实数据 |
| 手动控制（能力调节、预设操作、停止） | 开放，经安全限制 | 被控端钳制 + 锁存看门狗 |
| 设备实时监视（monitor） | 开放 | 被控端节流推送 |
| 蓝牙扫描/连接/配网、串口连接、固件升级、插线烧录 | 禁用 | 依赖被控端本机硬件交互与渲染进程，且风险高 |
| 游戏库 / 游戏配置 / 启动 / 停止 | 开放 | 见 §4.5 |
| 场景 | — | PC 客户端没有独立的「场景」功能；品牌设备的场景模式（如 pump `scene`）属于能力参数，随手动控制开放 |
| 插件、本地应用、浏览器 | 禁用 | 运行在被控端的 webview / 本地进程，无法远程渲染 |
| 设置、网络服务、日志、账号、测试 | 禁用 | 断开后可用 |
| 主控端自己的本机设备 | 远程状态下隐藏 | 断开后恢复；避免误把命令发给本机 |

### 4.0 实施路线调整（2026-10-06 动工前）

阅读现有实现后发现两条现成链路可直接组合，比「全量 REST 转译」更省、更稳：

- **设备投影**已把被控端设备以**同一设备 ID** 注册进主控端的 deviceService（`connectionType:'remote'`），状态按变化事件逐台推送（本身就是增量），写入经被控端 `sanitizeProjectionMessage` 钳制。所以主控端现有设备页、手动控制、页面式游戏不改代码即可驱动被控端设备；投影协议是设备消息级，移动端已兼容。
- **远程游戏**（`remoteGameService`）已是带白名单、授权、踢出、回执幂等的 RPC，含 `devices.rename`、`devices.controlConnection.set`、`games.list`、`game.*`。

因此远程会话 = **编排层 `remoteSessionService`**，同时拉起两条链路并统一授权：

1. 被控端「开启远程」：创建远程游戏房间（主房间，对外只给这一个房间码）+ 投影房间（TTL 取上限并自动续期）。
2. 主控端输入房间码加入主房间；被控端授权后，经主房间把投影房间码下发给该成员，主控端自动加入投影房间；被控端编排层对同一 userId 自动授权投影。
3. 撤销 / 踢出 / 急停 / 结束在两条链路上级联；任一链路断开按各自已有的重连与宽限处理，编排层只汇总状态。
4. 主控端进入远程模式后，本机后端对设备相关接口按会话过滤：设备列表只返回本会话投影来的设备；只能在被控端执行的写操作（昵称、控制连接切换）转成主房间 RPC；本机专属接口（蓝牙/串口/固件/插件/设置等）返回 `423 REMOTE_LOCKED`。preload 无需改写。
5. 被控端操作记录汇总两条链路的远程写入（含被钳制、被拒绝），急停 = 投影停输出 + 远程游戏停主控端触发的输出与玩法。

§4.2 的「REST→命令转译表」缩减为上面第 4 点的少量转发；§4.1 的语义命令仍是主房间协议，手机端将来实现同一命令集与投影协议即可。

### 4.1 线上协议：语义命令，不传 REST 路径

为远期手机端，网络上只传与平台无关的语义命令，沿用并扩展现有 `remoteGameService` 的 `COMMANDS` 白名单与信封（`messageId`、`sequence`、`gameSessionId`、回执缓存幂等）：

- 会话：`client.hello {platform, protocolVersion, features[]}`（双方据 `features` 降级，手机端可只实现子集）、`client.snapshot.request`。
- 设备：`devices.list`、`devices.rename`、`devices.controlConnection.set`、`devices.invoke`、`devices.operate`、`devices.stop`、`devices.monitor.subscribe/unsubscribe`。
- 游戏：`games.list`、`game.meta`、`game.config.get/set`、`game.start/stop/...`（HostRuntime 已有）。
- 推送（被控端→主控端）：`client.snapshot`、`devices.snapshot`（变更即推，去重）、`devices.patch`、`game.patch`（有变化才推增量）、`devices.monitor`（节流 ≥100ms）、`session.log`、`session.revoked`。

PC 专属的 REST 形状只存在于主控端本机的转译层，被控端只认语义命令。将来手机做被控端只需实现同一命令集；手机做主控端直接发命令即可。

### 4.2 主控端：一处切换，页面基本不改

- **preload 改写**：现有 `window.fetch` / `EventSource` 覆写已把 `/api/*` 指向本机后端（`electron/preload.js:427-441`）。远程模式下，命中「可远程路由表」的请求改写为 `/api/remote-session/forward/*`；未命中的被拦下返回 `423 REMOTE_LOCKED`，页面按普通错误显示。
- **转译表**（主控端后端）：`(method, path) → 语义命令 + 参数映射 + 回包映射`，例如 `GET /api/devices → 缓存的 devices.snapshot`、`POST /api/devices/:id/capabilities/:cap/:action → devices.invoke`。读请求优先读缓存，避免 DevicesView 每 3 秒轮询都打到网络。
- **SSE 重放**：`/api/devices/:id/monitor-stream` 在主控端变成 `devices.monitor.subscribe`，收到被控端推送后按原 SSE 格式输出，页面无感。
- **路由守卫 + 侧栏置灰**：禁用页面在路由层拦截；`useRemoteSession` composable 提供全局状态给远程条和置灰逻辑。
- 直接 `fetch` 散落在 DevicesView 等页面约 70 处，靠 preload 统一改写即可覆盖，不需要逐个改调用点；只有禁用功能的按钮需要加置灰。

### 4.3 被控端：执行与审计

- 把投影与远程游戏的房间、凭证刷新、重连、在线状态、授权/撤销/踢出抽成公共 `remoteSessionCore`；远程会话模式、设备投影、远程游戏都是它上面的「功能模块」，同一时刻一个房间。
- 每条命令：授权 userId 校验 → 白名单 → `remoteOutputGuard`（钳制 / 拒绝未知字段 / 停止永远放行）→ 调现有服务 → 回执 + 记录 `session.log`。
- 远程触发的输出登记到「主控端触发输出表」，供急停、踢出、掉线时只停主控端的输出（复用 `createOutputWatchdog`）。
- 投影出来的 `remote` 设备不再转发（已有规则），防止多跳。

### 4.4 实时同步

| 数据 | 方式 | 频率 |
|---|---|---|
| 设备列表与状态 | 被控端监听 `onDeviceListChange` / `onDeviceDataChange`，有变化推增量 `devices.patch`，进房/重连补全量 `devices.snapshot` | 事件驱动，50ms 窗口合并 |
| 监视曲线 | 订阅制 `devices.monitor`，仅在主控端打开监视时推 | 节流 100ms |
| 游戏状态 | 有变化才推增量 `game.patch`，进房/重连/丢包时补一份全量 `game.snapshot` | 事件驱动，同一 50ms 窗口内合并；无变化零流量 |
| 延迟 | `client.ping/pong` | 5s |


### 4.5 游戏：逻辑跟着设备走

原则：**有设备的一端跑逻辑**。要快速响应设备的游戏在被控端跑逻辑，主控端只渲染；不在乎延迟的游戏在主控端跑，通过设备映射驱动被控端设备。

| 游戏类型 | 逻辑在哪跑 | 画面 | 设备通路 |
|---|---|---|---|
| 分离式游戏（逻辑文件 + 画面文件） | 被控端 | 两端都有 | 被控端本机直连，「触发→判断→输出」不经网络 |
| 页面式游戏（逻辑与画面写在同一页面，现有大部分游戏） | 主控端 | 仅主控端 | 远程设备映射（已有），输出经被控端钳制 |
| 第三方代理游戏（未上架审核） | 主控端 | 仅主控端 | 同页面式；不允许以分离式运行 |
| 插件、本地应用 | — | — | 禁用（运行在被控端的 webview / 本地进程） |

**分离式游戏标准**（本方案新增，取代原「桥隧道」设计；契约与审核清单见
[docs/architecture/split-game-contract.md](../architecture/split-game-contract.md)）：

- 游戏包包含 `game-core.js`（逻辑）与画面页面。逻辑只暴露 `step({nowMs, events})`、`snapshot()` 和设备意图，不碰 DOM、计时器、网络；画面只渲染快照、发命令。契约沿用现有 `backend/game-runtime/gameCoreRuntime.js`。
- 本机游玩与远程游玩走同一套代码：本机时逻辑在本机后端跑、画面在本机；远程时逻辑在被控端后端跑，两端画面订阅同一份快照。
- 逻辑文件随游戏包从游戏库安装，不再写死在客户端里（现在三阶段寸止两个版本的逻辑写死在 `backend/game-runtime/cores/`，需迁出）。代码**不会**从主控端发往被控端，两端各用自己安装的同一游戏包；连接时比对 `gameVersion`，不一致提示旧的一端从游戏库更新。
- **安全靠上架审核，不做运行隔离**（用户 2026-10-06 决定）：只有官方游戏库中审核通过的游戏能以分离式运行，逻辑文件以普通 JS 在被控端后端加载；第三方代理游戏一律按页面式运行。设备输出仍经现有安全上限与锁存看门狗——这是输出层保护，不是代码隔离。
- **画面同步：有变化才发，只发变化部分**（取代现在的 500ms 定时全量推送）：
  - 被控端每次 `step` 后把新快照与上一份比对，有差异才发 `game.patch {rev, baseRev, ops}`，`ops` 只含变化的字段路径与新值；没有变化不发任何消息。
  - 合并：同一 50ms 窗口内的多次变化合并成一条，避免压力这类高频数据刷爆通道（上限约 20 条/秒）。
  - 补全量：主控端进房、重连，或发现 `baseRev` 对不上（丢包、乱序）时，请求一次全量 `game.snapshot`，之后继续收增量。
  - 曲线类数据（如压力采样）不逐点推送，而是随增量批量附带最近的采样点，主控端自行绘制。
  - 主控端按钮先显示「已发送」，收到被控端确认后更新。
  - 同一机制用于设备状态 `devices.snapshot`（§4.4），两处共用一套比对与补全量代码。
- 按需逐个改造：先排出「一触发就要立即输出」的游戏清单，只改这些；未改造的照常以页面式运行，游戏卡片标「远程时有延迟」。

生命周期：

- 分离式：沿用 HostRuntime；主控端掉线时游戏在被控端继续运行（09-23 决定），被控端随时可本地停止。
- 页面式：主控端运行，输出经设备映射；主控端掉线即停止其触发的输出（投影现有逻辑），不依赖 bridge 宽限。

## 5. 安全与仲裁

- **唯一网络入口**：被控端只接受来自已授权 userId 的 MQTT 命令（room JWT + broker ACL + 被控端授权三层）；本机后端仍只监听 127.0.0.1，远控路由保留 `loopbackOnly`。
- **输出上限**：全部远程输出在被控端钳制（默认电压 20 / 功率 128 / 强度 50）；锁存输出看门狗（电击 10s、电机 60s）；停止命令永远放行。
- **主控端掉线**：立即停主控端直接下发的手动输出和主控端运行的页面式游戏的输出；分离式游戏按 09-23 决定在被控端继续运行。
- **被控端与主控端冲突**：玩法按 ADR-0004「后启动者顶掉前者并复位」，被顶掉的一方收到提示；手动控制后写覆盖先写，被控端的急停与停止永远优先。
- **授权范围**：一次授权只在当前房间有效；撤销、踢出、房间结束后主控端立即失去所有能力并退回本机模式。
- **审计**：每条远程写操作（含被钳制、被拒绝的）写 `session.log` 推给被控端显示，并写入被控端本地日志。

## 6. 与 ADR 的关系

- ADR-0001（本机可信、bridge 不认证）在文末要求「联网时必须重审」。本方案的结论：bridge 依旧只对本机开放、不加认证；网络流量**不直接接触 bridge**，只经被控端后端的远程会话模块，在那里完成鉴权、白名单与钳制。实施时新增 **ADR-0012「远程会话是唯一网络入口」** 记录这一点。
- ADR-0004/0005：分离式游戏在被控端走 HostRuntime，唯一性与复位照旧。页面式游戏跑在主控端的 bridge 上，被控端的 bridge 看不到它，因此被控端把「主控端正在用映射设备运行游戏」登记为一个远程占用：被控端本地启动玩法时先停掉主控端的输出并通知主控端（被控端优先）；被控端本地玩法运行中，主控端启动页面式游戏会被拒绝并提示。
- ADR-0008：远程命令只到被控端的设备层，由被控端的单控制连接下发，不广播。

## 8. 风险与待验证

- **BLE 设备**：连接由被控端的渲染进程持有，被控端窗口最小化/节流时 GATT 写入是否及时需实测；扫描与连接只能在被控端做。
- **页面式游戏的延迟**：按压、压力等上行事件多一次网络往返，节奏类游戏应改为分离式；游戏卡片需标注。
- **审核责任**：不做运行隔离后，分离式游戏逻辑在被控端拥有后端权限，上架审核必须覆盖逻辑文件（禁止文件、网络、子进程等调用），审核清单需在步骤 5 补齐。
- **转译表维护成本**：新增页面接口忘记入表会表现为「远程不可用」，靠步骤 3 的覆盖测试兜住。
- **手机端**：本方案只保证协议可移植（语义命令 + `features` 协商），手机侧实现另立计划。

# 远程会话模式（客户端级远控）方案

> 状态：方案待审阅（2026-10-06）
> 承接：[2026-09-23-remote-game-client-control.md](2026-09-23-remote-game-client-control.md) §7「客户端级远控」，本文把它细化为可实施方案；游戏级远控（HostRuntime）沿用该文。
> 现状基础：远程设备投影、远程游戏两条链路已在生产 room API + EMQX 上回归通过（见 `docs/test/remote-control-e2e-2026-10-06.md`）。

## 0. 已确认决定（用户 2026-10-06）

1. 远程状态下开放：设备控制、游戏、场景；设置、插件、账号只读或禁用。
2. A 端要能看到 B 在做什么（操作记录），并可随时一键踢出。
3. 先做 PC↔PC；远期增加手机↔PC 互控 → **线上协议不得绑定 PC 后端的 REST 路径**。

## 1. 目标体验

B 连上 A 后，整个客户端切换到「A 的上下文」：设备列表、设备详情、手动控制、游戏库、游戏配置、游戏运行页显示的都是 A 的设备和状态，操作方式与操作本机一致。断开后回到本机。

不是屏幕推流：B 用自己的界面渲染，只有「请求 + 状态」走网络，延迟是一次 MQTT 往返（实测同城约 50–150ms）。

│ 浏览器 ⊘│  │ 强度 [===  ] │ │ 强度 [==   ] │                    │

- 入口：侧边栏新增「远程连接」页（合并现有远程游戏页与设备页里的投影面板）。输入房间码 → 等待 A 授权 → 自动进入远程模式并跳到「设备」。
- 远程条常驻：显示对方昵称、延迟、连接状态（重连中会变黄并锁住操作）；「急停」= 让 A 停止 B 触发的全部输出并结束 B 启动的玩法。
- 被踢 / 撤销 / A 离线超过宽限期：弹出说明，自动退回本机模式。

### 2.2 A 端（被控）

```
┌──────────────────────────────────────────────────────────────┐
│ ⚠ 小B 正在控制你的客户端     [ 操作记录 ▾ ] [ 急停 ] [ 踢出 ] │
└──────────────────────────────────────────────────────────────┘
  操作记录（最近 50 条，实时滚动）
  21:03:12  小B  设置「电击器 #3F2A」强度 30 → 已限制为 20
  21:03:05  小B  启动游戏《心跳挑战》
  21:02:40  小B  重命名「跳蛋 #91C0」→「左」
```

- 远程条在 A 端任何页面都可见，不可关闭；A 本地操作照常可用且优先。
- 「急停」：停 B 触发的所有输出 + 结束 B 启动的玩法；「踢出」：急停 + 踢出成员 + 关闭授权。
- 被钳制、被拒绝的操作也写进记录，方便 A 了解。

## 3. 功能范围

| 区域 | 远程状态 | 说明 |
|---|---|---|
| 设备列表 / 详情 / 昵称 / 控制连接切换 | 开放 | 读 A 的真实数据 |
| 手动控制（能力调节、预设操作、停止） | 开放，经安全限制 | A 端钳制 + 锁存看门狗 |
| 设备实时监视（monitor） | 开放 | A 端节流推送 |
| 蓝牙扫描/连接/配网、串口连接、固件升级、插线烧录 | 禁用 | 依赖 A 本机硬件交互与渲染进程，且风险高 |
| 游戏库 / 游戏配置 / 启动 / 停止 | 开放 | 见 §4.5 |
| 场景 | — | PC 客户端没有独立的「场景」功能；品牌设备的场景模式（如 pump `scene`）属于能力参数，随手动控制开放 |
| 插件、本地应用、浏览器 | 禁用 | 运行在 A 的 webview / 本地进程，无法远程渲染 |
| 设置、网络服务、日志、账号、测试 | 禁用 | 断开后可用 |
| B 自己的本机设备 | 远程状态下隐藏 | 断开后恢复；避免误把命令发给本机 |

## 4. 架构

```
 B 客户端                                             A 客户端
┌────────────────────────┐                          ┌──────────────────────────┐
│ Vue 页面（基本不改）     │                          │ 远程条 / 操作记录          │
│  fetch('/api/devices')  │                          │                          │
│        │ preload 改写   │                          │ RemoteSessionHost         │
│        ▼                │   rooms/{id}/commands/B  │  ① 鉴权（授权 userId）     │
│ B 后端 RemoteSession    │ ───────────────────────▶ │  ② 命令白名单              │
│  Operator               │   语义命令 + 桥帧         │  ③ remoteOutputGuard 钳制  │
│  · REST→命令转译表      │                          │  ④ 调本地服务执行          │
│  · A 状态缓存（读走缓存）│ ◀─────────────────────── │  ⑤ 写操作记录 / 回执       │
│  · SSE 重放             │   rooms/{id}/events      │ deviceService / bridge /  │
└────────────────────────┘   回执 + 状态推送         │ gameHostService           │
                                                      └──────────────────────────┘
```

### 4.1 线上协议：语义命令，不传 REST 路径

为远期手机端，网络上只传与平台无关的语义命令，沿用并扩展现有 `remoteGameService` 的 `COMMANDS` 白名单与信封（`messageId`、`sequence`、`gameSessionId`、回执缓存幂等）：

- 会话：`client.hello {platform, protocolVersion, features[]}`（双方据 `features` 降级，手机端可只实现子集）、`client.snapshot.request`。
- 设备：`devices.list`、`devices.rename`、`devices.controlConnection.set`、`devices.invoke`、`devices.operate`、`devices.stop`、`devices.monitor.subscribe/unsubscribe`。
- 游戏：`games.list`、`game.meta`、`game.config.get/set`、`game.start/stop/...`（HostRuntime 已有）、`play.bridge.*`（§4.5）。
- 推送（A→B）：`client.snapshot`、`devices.snapshot`（变更即推，去重）、`devices.monitor`（节流 ≥100ms）、`session.log`、`session.revoked`。

PC 专属的 REST 形状只存在于 B 本机的转译层，A 端只认语义命令。将来手机做被控端只需实现同一命令集；手机做主控端直接发命令即可。

### 4.2 B 端：一处切换，页面基本不改

- **preload 改写**：现有 `window.fetch` / `EventSource` 覆写已把 `/api/*` 指向本机后端（`electron/preload.js:427-441`）。远程模式下，命中「可远程路由表」的请求改写为 `/api/remote-session/forward/*`；未命中的被拦下返回 `423 REMOTE_LOCKED`，页面按普通错误显示。
- **转译表**（B 后端）：`(method, path) → 语义命令 + 参数映射 + 回包映射`，例如 `GET /api/devices → 缓存的 devices.snapshot`、`POST /api/devices/:id/capabilities/:cap/:action → devices.invoke`。读请求优先读缓存，避免 DevicesView 每 3 秒轮询都打到网络。
- **SSE 重放**：`/api/devices/:id/monitor-stream` 在 B 端变成 `devices.monitor.subscribe`，收到 A 推送后按原 SSE 格式输出，页面无感。
- **路由守卫 + 侧栏置灰**：禁用页面在路由层拦截；`useRemoteSession` composable 提供全局状态给远程条和置灰逻辑。
- 直接 `fetch` 散落在 DevicesView 等页面约 70 处，靠 preload 统一改写即可覆盖，不需要逐个改调用点；只有禁用功能的按钮需要加置灰。

### 4.3 A 端：执行与审计

- 把投影与远程游戏的房间、凭证刷新、重连、在线状态、授权/撤销/踢出抽成公共 `remoteSessionCore`；远程会话模式、设备投影、远程游戏都是它上面的「功能模块」，同一时刻一个房间。
- 每条命令：授权 userId 校验 → 白名单 → `remoteOutputGuard`（钳制 / 拒绝未知字段 / 停止永远放行）→ 调现有服务 → 回执 + 记录 `session.log`。
- 远程触发的输出登记到「B 触发输出表」，供急停、踢出、掉线时只停 B 的输出（复用 `createOutputWatchdog`）。
- 投影出来的 `remote` 设备不再转发（已有规则），防止多跳。

### 4.4 实时同步

| 数据 | 方式 | 频率 |
|---|---|---|
| 设备列表与状态 | A 监听 `onDeviceListChange` / `onDeviceDataChange`，推 `devices.snapshot`（整表，内容去重） | 变化时，最快 250ms 一次 |
| 监视曲线 | 订阅制 `devices.monitor`，仅在 B 打开监视时推 | 节流 100ms |
| 游戏状态 | HostRuntime 已有 `game.snapshot` | 500ms |
| 延迟 | `client.ping/pong` | 5s |


### 4.5 游戏

| 游戏类型 | 逻辑在哪跑 | 做法 |
|---|---|---|
| HostRuntime 游戏（三阶段寸止等） | A | 沿用现有远程游戏链路：A 执行，B 以 `runtime=remote` 渲染同一游戏页 |
| 经典游戏（页面自驱动，现有大部分游戏） | B 的页面 | **桥隧道**：游戏页仍连 B 本机 `/bridge`，B 后端在远程模式下把桥帧转成 `play.bridge.*` 发给 A；A 的 bridgeService 把它当成一个普通会话处理 |
| 第三方代理游戏 | B 的页面 | 同经典游戏；沙箱与代理白名单不变 |
| 插件、本地应用 | — | 禁用（运行在 A 的 webview/本地进程） |

桥隧道的要点：

- A 端会话生命周期完全沿用 ADR-0004/0005：全局唯一玩法、顶掉即复位、退出信号复位、断开 60 秒宽限后兜底复位。远程会话只是 bridge 的另一种「连接」，不新增玩法状态。
- 允许的桥帧：`invoke`（过 `sanitizeCapabilityInvoke`）、`read/readValue`、`subscribe*`、`getDevices/getDeviceMap`、`log`；`writeProps/sendMessage/operate` 过 `sanitizeProjectionMessage`，过不了就拒绝。
- `deviceMap` 里只能出现 A 的本机设备 ID。
- 游戏资源在 B 本地加载，缺失时按现有 `resolveGamePagePath` 安装；逻辑在 B 跑，不存在双端版本不一致问题。
- **取舍**：经典游戏的画面只在 B 端显示，A 端远程条显示「小B 正在运行《X》」+ 急停。要让 A 也看到画面，必须把游戏改造成 HostRuntime，属于 09-23 方案的游戏级远控，不在本方案范围。

## 5. 安全与仲裁

- **唯一网络入口**：A 只接受来自已授权 userId 的 MQTT 命令（room JWT + broker ACL + A 端授权三层）；本机后端仍只监听 127.0.0.1，远控路由保留 `loopbackOnly`。
- **输出上限**：全部远程输出在 A 端钳制（默认电压 20 / 功率 128 / 强度 50）；锁存输出看门狗（电击 10s、电机 60s）；停止命令永远放行。
- **B 掉线**：立即停 B 直接下发的手动输出；B 运行的经典游戏按 ADR-0005 宽限 60 秒后复位；HostRuntime 游戏按 09-23 决定在 A 继续运行。
- **A 与 B 冲突**：玩法按 ADR-0004「后启动者顶掉前者并复位」，被顶掉的一方收到提示；手动控制后写覆盖先写，A 的急停与停止永远优先。
- **授权范围**：一次授权只在当前房间有效；撤销、踢出、房间结束后 B 立即失去所有能力并退回本机模式。
- **审计**：每条远程写操作（含被钳制、被拒绝的）写 `session.log` 推给 A 显示，并写入 A 本地日志。

## 6. 与 ADR 的关系

- ADR-0001（本机可信、bridge 不认证）在文末要求「联网时必须重审」。本方案的结论：bridge 依旧只对本机开放、不加认证；网络流量**不直接接触 bridge**，只经 A 后端的远程会话模块，在那里完成鉴权、白名单与钳制。实施时新增 **ADR-0012「远程会话是唯一网络入口」** 记录这一点。
- ADR-0004/0005：远程经典游戏复用 bridge 会话生命周期，不新增状态来源（见 §4.5）。
- ADR-0008：远程命令只到 A 的设备层，由 A 的单控制连接下发，不广播。

## 8. 风险与待验证

- **BLE 设备**：连接由 A 的渲染进程持有，A 窗口最小化/节流时 GATT 写入是否及时需实测；扫描与连接只能在 A 端做。
- **经典游戏的传感器延迟**：按压、压力等上行事件多一次网络往返，节奏类游戏手感需实测；必要时对属性订阅做合并推送。
- **转译表维护成本**：新增页面接口忘记入表会表现为「远程不可用」，靠步骤 3 的覆盖测试兜住。
- **手机端**：本方案只保证协议可移植（语义命令 + `features` 协商），手机侧实现另立计划。

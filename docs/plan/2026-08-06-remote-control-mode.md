# 远程对战/控制玩法实施计划

> 状态：设计定稿，待动工
> 前置调研：`packages/api` 房间系统评估（见本文 §5）

## 0. 背景与目标

现有游戏全部是单机架构。客户提出「想远程一起玩」，落地形态为**异地 1v1**：一人戴硬件被远程驱动，另一人远程发出指令。

**核心决策（已确认）：**
- 被控端与主控端是**同一个游戏包 `remote-play` 的两个视角**
- 两侧都跑在客户端上（PC 面板 / 手机 App），不走浏览器网页
- 复用移动端 `packages/api` 的房间系统 + MQTT 通道

**商业定位**：生态功能，服务硬件销售。被控方是硬件买家；主控方零门槛（客户端 + 房间码即玩），是潜在拉新入口。不直接商业化。

## 1. 一个游戏，两个视角

游戏包 `remote-play`，与现有 6 个游戏完全平级，启动时先选身份：

```
被控方（host）                        主控方（player）
PC 面板 / 手机 App                    PC 面板 / 手机 App
┌──────────────┐                     ┌──────────────┐
│ 游戏列表      │                     │ 游戏列表      │
│ └ remote-play│                     │ └ remote-play│
│   ↓ 启动      │                     │   ↓ 启动      │
│ 选「当被控」  │                     │ 选「当主控」  │
│ 选设备映射    │                     │ 输房间码     │
│ 显示房间码   │ ←──MQTT broker──→   │ 看到遥控面板 │
│ 收指令驱动设备│                     │ 发指令       │
└──────────────┘                     └──────────────┘
```

**「一个游戏」的体现：**
- 同一个 `gameId=remote-play`、同一份代码包、同一个 `gameVersion`
- 两侧共享同一份协议定义（指令格式 / 传感器数据格式 / 状态同步格式）
- `gameVersion` 作为协议版本：主控被控版本不兼容时进房即提示升级，不进入会话

**身份判断**：游戏启动后第一个界面让用户选「我要被控 / 我要主控」，不做自动探测。

## 2. 两侧职责

| | 被控视角 | 主控视角 |
|---|---|---|
| 启动后 | 选设备映射 → 创建房间 → 显示房间码 | 输房间码 → 请求加入 |
| 持有连接 | DeviceAPI + RoomClient(host) | RoomClient(player) |
| 设备 | 驱动本地设备 | 无设备 |
| 界面 | 传感器读数 + 房间码 + 紧急停止 | 传感器读数 + 控制按钮 |
| 主控掉线 | 超 10 秒 → 设备复位 + 结束 | 提示断开 |
| 被控掉线 | —（房间关闭） | 提示房间已关闭 |

**主控能控什么，完全取决于被控方启动时映射了什么设备**：
- 被控方映射了电击 → 主控看到电击按钮
- 被控方映射了振动 → 主控看到振动滑杆
- 未映射的能力 → 主控界面不显示对应控件
- 被控方进房后把「本次映射的能力清单」作为第一条消息发给主控，主控据此动态渲染界面

## 3. 连接流程

```
被控方                              主控方
  │                                   │
  ├─ 启动 remote-play                 │
  ├─ 选「当被控」                      │
  ├─ 选设备映射（复用现有框架）          │
  ├─ 设本次上限（电击/振动最大值）       │
  ├─ 创建房间 → 显示房间码               │
  │                                   │
  │  ←──── 微信/QQ 发码给对方 ──────→  │
  │                                   ├─ 启动 remote-play
  │                                   ├─ 选「当主控」
  │                                   ├─ 输房间码
  │                                   │
  ├─ 弹「XX 请求接管，允许？」          │
  ├─ 点【允许】←───────────────────── │
  │                                   │
  ▼ 进入会话                           ▼ 看到遥控面板
```

**规则：**
1. 房间码沿用后端现有格式（base64url 随机串），10 分钟无人加入自动失效。
2. **被控方必须显式点允许**，主控才能看到任何数据或发出任何指令（不可跳过）。
3. 被控方点允许**之前**先设本次上限（最大电击强度、最大振动力度、是否允许锁操作）。主控所有指令被钳制在上限内。
4. 连接建立后房间码立即作废，防第三人闯入（capacity=2，一主控一被控）。
5. 任一方主动退出 → 通知对方 → 房间关闭。

## 4. 玩法模式

### 模式 1：自由遥控（v1）

主控界面是遥控器面板：

```
┌─────────────────────────────┐
│  对方的状态           🟢在线 │
│  ─────────────────────────  │
│  提肛压力  ▓▓▓▓▓▓░░ 62%     │
│  踮脚压力  ▓▓▓░░░░░ 35%     │
│  ─────────────────────────  │
│  ⚡ 电击    [弱][中][强]     │
│  〰️ 振动    [滑杆 ━━━●──]   │
│  🔒 锁      [锁定/解锁]      │
└─────────────────────────────┘
```

- 主控实时看到被控方在线传感器读数（500ms 刷新）。
- 主控点按钮 → 指令经 MQTT → 被控方 → DeviceAPI → 本地设备。
- 只渲染被控方实际映射了的能力控件。
- 无胜负、无流程，纯互动。这是最小验证单元。

### 模式 2：任务指令（v2）

主控从任务库派任务，被控方接受后跑判定，主控实时看进度。

**复用方案（已定为「接法 2」）：不加载现有游戏，在 remote-play 内重写轻量判定。**

现有游戏是自包含 IIFE 页面，判定状态机/阈值/计数封装在游戏内部，**不是可外部调用的模块**，无法「远程启动 pushup-detection 并接管它的判定」。因此：

- remote-play 任务模式**自己实现简化版判定状态机**，复用现有游戏的**判定参数与思路**（非代码）：
  - 任务「做 20 个俯卧撑」→ 订阅 distance 传感器，用 `pushup-detection` 的 `downThreshold:15 / upThreshold:35` 跑简化计数状态机
  - 任务「提肛保持 30 秒」→ 订阅 sphincterPressure，参考 `pelvic-training` 的 `pressureDelta:0.3` 跑简化保持判定
- 传感器输入走被控方本地 DeviceAPI（与现有游戏同一条通道，现成）
- **现有游戏零改动**，符合「对游戏透明」原则
- 代价：判定逻辑两份（原游戏 + remote-play 简化版），v2 只接 2-3 个任务，量可控

**不选「抽公共判定模块」重构现有游戏**：工作量大、动到跑得好的代码，违背游戏零改动原则。任务模式的判定本就比完整游戏简单（只判成败，不要完整 UI/阶段/奖励）。

| 主控可选任务 | 判定参数来源 | 失败惩罚 | 成功奖励 |
|---|---|---|---|
| 提肛保持 30 秒 | `pelvic-training` 的 pressureDelta | 电击 1 次 | 振动 5 秒 |
| 做 20 个俯卧撑 | `pushup-detection` 的 down/upThreshold | 电击 1 次 | 跳蛋 10 秒 |
| 踮脚站 2 分钟 | `maid-punishment` 踮脚判定 | 寸止加强 30 秒 | 解除锁定 |
| 喝 500ml 水 | `drink-pee-unlock` 称重判定 | 锁定延长 10 分钟 | — |

### 模式 3：Edging 接管（v3）

主控实时看气压曲线，手动干预 TD01 强度，决定何时放行。复用 `pressure-edging-v2` 状态机，把自动调节决策权换成主控输入。

**v1 只做模式 1。**

## 5. 系统架构：复用移动端房间系统

### 5.1 复用决策

调研结论（详见调研记录）：
- `packages/api` 的房间系统骨架**可直接复用**：1v1 房间（capacity=2）、joinCode、匿名接入、MQTT + JWT ACL、断连清理都是生产级
- 移动端的设备桥接**不可复用**：action grant 是本地闭环半成品，无传感器上行，无远程指令链路
- 因此：**复用后端 + MQTT + room-sdk，新写游戏内的远程控制逻辑**

### 5.2 架构图

```
被控方客户端                          主控方客户端
┌──────────────────┐                 ┌──────────────────┐
│ remote-play 游戏  │                 │ remote-play 游戏  │
│  被控视角         │                 │  主控视角         │
│                  │                 │                  │
│  DeviceAPI ──────┼──→ 本机 bridge ──→ 本地设备          │
│  RoomClient(host)│                 │  RoomClient(player)│
└────────┬─────────┘                 └────────┬─────────┘
         │                                    │
         └────────────┬───────────────────────┘
                      ↓ MQTT (wss)
              ┌──────────────┐
              │ EMQX broker   │
              │ (房间系统现有) │
              └──────┬───────┘
                     ↓ REST
              ┌──────────────┐
              │ packages/api  │
              │ 房间生命周期   │
              │ JWT 签发      │
              └──────────────┘
```

### 5.3 通道映射

复用现有 topic 结构，角色映射为**被控=host，主控=player**：

| 数据流 | topic | 方向 |
|---|---|---|
| 指令下行 | `rooms/{id}/commands/{主控id}` | 主控(player)发 → 被控(host)收 |
| 传感器上行 | `rooms/{id}/events` | 被控(host)发 → 主控(player)收 |
| 私聊/握手 | `rooms/{id}/private/{对方id}` | 双向 |

**为什么这个方向能成立：**
- host 掉线自动关房 = 被控方掉线会话结束，语义正确
- host 能订 `commands/+` 收主控指令，能发 `events` 广播传感器，权限刚好够用
- player 只能发 `commands/{自己}` 给 host，不能骚扰别人，权限收敛
- broker 和 ACL **不用改**

### 5.4 框架改动评估（已核实）

**后端 `packages/api`：零改动。**
- joinCode 沿用后端现有实现（`createRoomJoinCode`，base64url 随机串），不改格式。
- 房间生命周期 / JWT ACL / MQTT topic / 断连清理均直接用，capacity=2 即可。

**room-sdk（TS 包）：零改动。**
- `publishCommand`（主控发指令）/ `publishEvent`（被控发 telemetry）/ `onCommand` / `onEvent` 完全够用，语义正好。

**手机端框架：零改动。**
- 已有 `room_api_bridge_js.dart`（RoomAPI 9 个方法）+ `room_bridge.dart`，游戏 JS 经 `getMqttCredential` 拿凭证后用 room-sdk 直连 MQTT。

**PC 面板框架：从零新写 RoomBridge（v1 唯一框架层工作量，当前完全不存在）。**
- 已核实 PC 面板 backend/electron/frontend/play-registry 中无任何 RoomAPI/RoomBridge/房间相关代码，PC 游戏现仅有 DeviceAPI 一条通道。
- 需照抄手机端实现：
  1. PC 版 `RoomAPI` JS facade（同手机端 9 个方法）
  2. PC 版 RoomBridge 主进程处理器（调 `packages/api` REST 拿凭证）
  3. 游戏 iframe 加载 room-sdk 编译产物

**钳制与心跳的落点（v1 决策）：**
- 手机端现状是游戏 JS 直连 MQTT（主进程不在数据路径上）。
- **v1 跟随手机端现状：游戏直连 MQTT，强度钳制与 30 秒心跳逻辑写在游戏代码内。** v1 是自家可信游戏代码，够用。
- 主进程代理层（钳制/心跳上移到主进程，防游戏代码被篡改）**留到 v2 支持第三方游戏时再做**。这样 PC 框架 v1 只写 RoomBridge（拿凭证），不写代理层，手机端框架完全不动。

## 6. 协议设计

### 6.1 握手消息（被控 → 主控，进房第一条）

```json
{
  "type": "session.hello",
  "gameVersion": "1.0.0",
  "capabilities": [
    {"logicalId": "punish", "kind": "shock", "maxVoltage": 30},
    {"logicalId": "vibe",   "kind": "strength", "maxStrength": 80},
    {"logicalId": "sensor", "kind": "sphincterPressure"},
    {"logicalId": "qtz",    "kind": "tiptoePressure"}
  ],
  "limits": {"shockVoltage": 20, "vibeStrength": 50, "lockAllowed": false}
}
```

主控据此渲染界面；`limits` 是被控方设的上限，**主控界面必须把上限渲染出来**（电击滑杆最大值=上限，或标注「上限 20V」），让主控明确知道边界，不只是协议层传递。

### 6.2 指令消息（主控 → 被控）

```json
{"type": "cmd.shock", "voltage": 15, "durationMs": 1000}
{"type": "cmd.vibe",  "strength": 60}
{"type": "cmd.lock",  "open": true}
{"type": "cmd.stopAll"}
```

被控侧收到后：钳制到 limits → 翻译成 DeviceAPI 调用 → 驱动设备。

### 6.3 传感器上行（被控 → 主控，500ms）

```json
{
  "type": "telemetry",
  "ts": 1234567890,
  "data": {"sphincterPressure": 62, "tiptoePressure": 35, "weight": 58.3}
}
```

只上行被控方实际映射了的传感器。

### 6.4 心跳与掉线

- 主控每 10 秒发 `ping`，被控 30 秒收不到 → 判定主控掉线 → 设备复位 + 结束会话
- 被控掉线 → host 离开 → 房间自动关闭（复用现有机制）→ 主控收到房间关闭事件

## 7. 安全设计（不可裁剪）

| 机制 | 实现位置 |
|---|---|
| 显式允许（被控点允许前主控无权限） | 游戏 UI（v1） |
| 强度上限钳制 | 游戏代码内（v1，自家可信代码）；主进程代理（v2 起，防第三方篡改） |
| 紧急停止悬浮按钮 | 被控视角 UI（复用现有退出信号） |
| 主控掉线 30 秒设备复位 | 游戏代码内心跳监测（v1）；主进程代理（v2 起） |
| 房间码一次性 + 10 分钟过期 | packages/api（现有） |
| 版本不兼容拒绝进房 | 游戏握手 |
| 会话本地日志（时间/时长/操作数，不含内容） | 客户端本地 |

## 8. 版本节奏

### v1（最小可行）— 自由遥控
- **后端**：零改动，沿用现有房间系统与 joinCode
- **PC 面板**：从零新写 RoomBridge（RoomAPI facade + 主进程凭证处理 + 加载 room-sdk）——当前 PC 无任何房间代码
- **手机端**：框架零改动，复用现有 room bridge
- **`remote-play` 游戏包**：身份选择 + 被控视角（建房/显码/允许/驱动设备/紧急停止）+ 主控视角（输码/遥控面板，渲染上限）
- 游戏内实现：强度钳制 + 30 秒心跳（跟随手机端直连模式）
- 只支持电击 + 振动两个能力，传感器上行
- 安全四件套（允许 / 上限 / 紧急停止 / 掉线复位）

### v2 — 任务指令模式
- 任务库 + 派发流程，判定复用现有游戏（先接 `pushup-detection` 和 `pelvic-training`）
- 主控端进度条

### v3 — Edging 接管
- 气压曲线实时上行
- 主控干预接 `pressure-edging-v2` 状态机

### v4 — 更多能力 + 拉新闭环
- 锁操作、更多传感器
- 会话结束页引导主控「也想被控？买设备 →」导淘宝

## 9. 待决策项（动工前需定）

1. **房间码接入**：输码（最简单）vs 扫码（被控方展示二维码，主控扫）。建议 v1 先输码，v2 加扫码。
2. **互动媒介**：v1 纯按钮（无审核风险），文字/语音指令留到 v2 再评估。
3. **MQTT broker 部署**：复用移动端现有 broker 即可，需确认其容量和地域是否够用。
4. **游戏上架**：`remote-play` 进 play-registry 的方式，版本号规则同现有游戏。

> 注：手机端设备能力是完整的（`lib/features/games/runtime/capabilities.dart` 注册 9 种能力，对标 PC 后端能力层），手机端可当全功能被控，v1 无需限定 PC。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 远程延迟影响手感 | v1 先验证；指令走 MQTT QoS1；broker 部署在靠近用户的区域 |
| 内容合规风险 | 1v1 私密房间；无公开列表；无内容存储；v1 纯按钮无 UGC |
| 主控方身份不可控 | 房间码被控方主动分发；显式允许；会话日志留痕 |
| 房间系统预留字段未实现（hostEpoch 等） | 不影响本玩法；host 迁移等高级特性后续按需 |

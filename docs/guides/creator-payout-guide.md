# 创作者月度分成运营指南（管理员）

- 面向：投稿平台审核管理员
- 更新：2026-10-06
- 相关代码：`game-platform/`（后端）、`play-registry/admin.html`（审核后台「月度分成」tab）

## 一句话流程

OpenPanel 看板手工统计 → 商城后台手工发奖励金 → 回投稿平台录入发放记录 → 作者在「我的分成」看到。

系统**不拉 OpenPanel**，也**不参与算钱**：没有奖金池、没有门槛参数，金额完全由管理员按当月情况决定。
投稿平台只保存「谁、哪个月、哪个游戏、发了多少钱」这条记录。

## 1. 埋点在哪

游玩结束事件是统计的基础，PC 和手机是两个不同的 client（项目），字段也不完全一样。

### PC（控制面板客户端）

- 事件名：`game_stop`（插件玩法是 `plugin_stop`，分成不涉及）
- 代码：`frontend/src/playAnalytics.ts`、`frontend/src/playSession.ts`
- 属性：

  | 属性 | 说明 |
  | --- | --- |
  | `game_id` | 玩法 ID，就是分成的归属键 |
  | `version` | 玩法版本号 |
  | `source` | 来源：社区 / 官方内置 / 本地上传 / 外部 URL |
  | `device_macs` | 本次映射到的设备标识，逗号分隔 |
  | `device_count` | 映射设备数量 |
  | `duration_ms` | 本次游玩时长（毫秒） |
  | `end_reason` | 结束原因（user_stop / leave / replaced 等） |

- 注意：`game_id` 等字段是 **1.0.36 beta 起**才带上（对应 `frontend` 版本 1.0.36-beta.x）。更早的正式版只有设备与时长，
  没有 `game_id`，**那些数据不能用来结算**。

### mobile（App）

- 事件名：`game_exit`
- 代码：`control_panel_mobile` 仓库 `lib/core/analytics/analytics.dart`（`game_exit` 随下个 App 版本发布）
- 属性：`game_id`、`version`、`source`（`asset` / `remote` / `cached`）、`device_macs`、
  `device_count`、`duration_ms`、`session_duration_ms`、`exit_reason`
- 注意：
  - `duration_ms` 是新字段，老版本只有 `session_duration_ms`；两个字段都看，缺一个就用另一个。
  - **iOS 的设备标识是 UUID，不是 MAC**，和 Android 的 MAC 不能互相去重；跨端不要把设备数直接相加。
  - `source = asset` 是 App 内置资源，不是社区游戏。

## 2. 在 OpenPanel 看板按月统计

看板地址 <https://op.shiroha.tech>（自建）。PC 与 mobile 是**两个 client / 两个项目**，需要分别看。
海外网络不通时走 HTTP 代理 `127.0.0.1:7990`。

官方文档里写明的能力（`Understand the overview`、`Export`、`Insights`、`MCP Server` 页）：

- 概览页（Overview）顶部有 **Top stats** 指标卡，右上角可选 **Range**（Today / Last 7 days / Last 30 days … 或自定义区间）
  和 **Interval**（hour / day / week / month）。
- 概览页底部有 **Events** 组件，列出所选区间里自定义事件（`game_stop` / `game_exit` 就在这里），按次数排序；
  点击某个事件会把整个概览页过滤成「触发过该事件的会话」。
- **Filters and time controls**：全局 Range、Interval、Event filter，以及点任意组件里的行（国家、来源、页面）
  会加一个维度过滤，生效的过滤条件显示成可删除的 chip。
- 还有 Devices（设备/浏览器/系统维度）、Geo、Activity heatmap、User Journey 等组件。
- 想批量导出原始事件用 `GET /export/events`（分页、可过滤），要聚合时序数据用 `GET /export/charts`；
  两者都需要 **read 权限** client。

推荐做法（每一步的界面细节**以看板实际界面为准**，不同版本菜单名可能不同）：

1. 打开对应项目（先 PC，再 mobile），Range 选**上一个自然月**（或自定义起止日期）。
2. 用 Event filter 或直接点 Events 组件里的 `game_stop` / `game_exit`，把范围收窄到这个事件。
3. 按 `game_id` 过滤或分组：看板若支持按事件属性分组/下钻，就用它按 `game_id` 拆开看每个游戏；
   如果当前版本没有属性分组入口，就逐个 `game_id` 用过滤条件（属性 = `game_id`，值 = 具体玩法 id）单独看一次。
   **这两条都要以看板实际界面为准。**
4. 看时长：用 `duration_ms`（mobile 老数据用 `session_duration_ms`）过滤掉明显过短的记录，
   比如只看 ≥ 几分钟的。阈值当场定，不用写死。
5. 记录每个游戏的**独立设备数**（主参考）和**游玩次数**（次参考）。
6. 也可以走 MCP（`https://api.openpanel.dev/mcp`，自建实例把域名换成自己的）让 AI 助手直接查：
   `list_event_names`、`list_event_properties`、`get_event_property_values`、`query_events`、
   `find_profiles` 这些工具是官方文档列出的，适合快速核对某个游戏某个设备的记录。

### 看板做不到的事怎么近似

看板能给的是「事件数」和「独立设备数」，**做不到「同一设备同一天只算 1 次」**这种去重
（这需要按设备 + 日期做二次聚合）。近似办法：

- **以独立设备数为主**：一个设备反复玩不会把数字撑起来，比次数可靠。
- **以游玩次数为辅**：次数明显远大于设备数时，说明有复玩，也可能有刷量，看两者比例判断。
- 需要更细的判断时，用 `GET /export/events` 或 MCP 的 `query_events` 拉原始事件，
  在本地按 `device_macs` + 日期自己去重。

### 刷量识别提示

- 同一个设备标识在短时间内大量 `game_stop` / `game_exit`。
- `duration_ms` 集中在很短的一段时间（几秒到几十秒）但次数很多。
- `device_macs` 为空或异常（没有映射真实设备）。
- 同一 `device_macs` 出现在多个账号/多个 game_id 下。
- iOS 的 UUID 会变：同一台 iPhone 重装后是新 UUID，会看起来像「新设备」；不要当成刷量。
- 官方内置玩法（PC 的 `source` 是官方内置、mobile 的 `source = asset`）不参与分成，出现即忽略。

## 3. 找作者

审核后台 <https://game.undersilicon.cn/admin.html> →「月度分成」tab：

- **社区游戏与作者**列表：游戏 ID、标题、当前版本、作者名、**作者邮箱**、**账号中心 ID**、状态（已上线 / 已下架）。
  官方内置玩法不在列表里。
- 状态为「已下架」的游戏默认不出现在录入表单的游戏下拉里，但当月已经发过钱的仍能查到记录。
- 找不到某个游戏时，多半是导入时没有投稿记录（例如线上 `surge-edging`），去 tab 底部的「归属指定」认领。

## 4. 发钱（商城后台）

- 入口：商城后台 `/admin/reward`（「奖励金发放」）。
- **当前线上版本只支持按「账号 ID」查询**（`/api/admin/reward?accountNo=...`）。
  商城仓库分支 `feat/reward-lookup-by-account` 已加上按**邮箱**和**账号中心 ID** 查询，
  **该分支尚未上线**；上线前只能拿审核后台列表里的「账号中心 ID」去查（账号 ID 与账号中心 ID 的对应关系
  以商城后台实际显示为准）。
- 查到用户后「增加奖励金」，备注统一写成：

  ```
  创作者分成 YYYY-MM <game_id>
  ```

  例如 `创作者分成 2026-09 surge-edging`。备注会显示在作者商城流水里，方便对账。
- 作者还没登录过商城（商城里没有对应用户）：先不录发放记录，通知作者用同一账号登录一次商城，
  下月一并补发。

## 5. 回投稿平台录入

1. 打开审核后台「月度分成」tab。
2. 表单填：**月份**（默认上月）、**游戏**（下拉，只列社区游戏）、**有效游玩**（选填，从 OpenPanel 手抄的参考数据）、
   **金额（元，必填，> 0）**、**备注**（选填，建议写商城账号或批次）。
3. 提交。作者按 `game_id` 归属自动带出，**不需要手填作者**。
4. 常见报错：
   - 「该游戏 ID 不是社区游戏（没有归属作者），不能录入分成」→ 官方内置玩法或还没指定归属的导入游戏；
     确实属于社区作者的，先去「归属指定」。
   - 「该游戏这个月已经录入过发放记录」→ 同月同游戏只允许一条；先删除原记录再重录。
   - 「金额必须大于 0 元」→ 金额填 0 或负数会被拒。
5. 录入后作者在投稿工作台「我的分成」里能看到月份、游戏、有效游玩（如填了）、金额、发放时间、备注。
6. **录错了**：在「发放记录」里点该行的「删除」，确认后重新录入即可。删除是彻底删除，不会留痕。

## 6. 归属指定什么时候用

正常投稿上架的游戏，归属自动是**第一个发布它的作者**，不用管。需要手工指定的是这类情况：

- 游戏是**导入**进平台的（只有官方 release，没有投稿记录），实际是社区作者做的。
  典型例子：线上 `surge-edging`（气压突变寸止）是非管理员作者 **DK** 的社区游戏，
  团队仓库里还在维护它的新版本，需要管理员去发布更新。
- 需要把这类游戏指定给作者，之后才能给它录入分成，作者本人也才能自己升版更新。

操作：审核后台「月度分成」tab →「归属指定」→ 填**游戏 ID**、**作者邮箱**、**署名** → 指定。

- 作者邮箱必须是**已经在投稿平台登录过**的邮箱（`identities` 里有记录），否则报
  「该邮箱尚未登录过投稿平台」；让作者先用这个邮箱登录一次投稿工作台即可。
- 指定后该游戏视为社区游戏：出现在社区游戏列表里、可录入分成、作者本人可升版更新。
- 可以重新指定，以最后一次为准。

### 归属判定优先级（最终）

1. `game_owners` 表里的**手工指定**（最高）
2. **最早的社区 release 的作者**（正常投稿）
3. **官方保留**（最早一条 release 没有投稿记录）——只有管理员能发布更新

### 版本规则（两条规则要记住）

- **管理员投稿可以发布到任何已存在的 `game_id`**（官方 ID、他人的社区游戏、指定归属的游戏），
  方便团队继续维护已上线的社区游戏；**归属不变**，仍是原作者。
- **版本必须严格升高**（semver，`1.4.1 → 1.5.0` 可以，`1.4.1 → 1.4.1` 不行），管理员也一样。
- 其他作者用已存在的 `game_id` 一律拒绝。

审核后台的投稿标记：`新游戏` / `更新（原作者）` / `管理员更新` / `官方 ID` / `ID 冲突`。
出现 `ID 冲突` 时「批准发布」会被拦下，服务端也会拒。

## 7. 每月检查清单

- [ ] 确认上月 PC 端有 `game_id` 的数据可用（1.0.36 beta 起的版本）；老版本数据不计。
- [ ] OpenPanel 里分别看 PC 项目（`game_stop`）和 mobile 项目（`game_exit`）。
- [ ] 逐个社区游戏记录**独立设备数**（主）与**游玩次数**（次）；iOS 的 UUID 不与 Android MAC 混算。
- [ ] 排除官方内置玩法、明显刷量记录、内部/测试设备。
- [ ] 对照审核后台「社区游戏与作者」列表，确认每个游戏都能找到作者邮箱与账号中心 ID。
- [ ] 发现导入的社区游戏还没归属 → 先在「归属指定」里认领。
- [ ] 在商城后台 `/admin/reward` 按账号增加奖励金，备注写 `创作者分成 YYYY-MM <game_id>`。
- [ ] 作者还没登录过商城 → 不录记录，通知登录，下月补发。
- [ ] 回审核后台「月度分成」逐条录入发放记录，核对金额。
- [ ] 抽查 1–2 个作者，登录投稿工作台确认「我的分成」里能看到。
- [ ] 录错的记录及时删除重录；月底再和商城流水对一次账。

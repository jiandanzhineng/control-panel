# 游戏 `TESTING.md` 编写指南

每个可发布游戏都必须在自己的游戏目录中提供一份简洁、可读、可执行的 `TESTING.md`。它既用于让人确认整体玩法是否符合预期，也用于让 Agent 按相同标准完成虚拟设备和实机测试。

本指南只规定 `TESTING.md` 的内容和维护要求。游戏运行、设备能力和 Electron 调试方式分别参考：

- [游戏与玩法运行时说明](../requirements/Game_Runtime.md)
- [设备能力说明](../device/capabilities.md)
- [Electron 调试速查](ELECTRON_DEBUG.md)
- [虚拟设备命令行工具](../../tools/vdev-cli/README.md)

## 一、文件位置

`TESTING.md` 必须和游戏代码放在同一目录：

```text
backend/games/<game-id>/TESTING.md       # 内置游戏
play-registry/games/<game-id>/TESTING.md # 在线扩展游戏
```

新增游戏时必须同时新增该文件。修改玩法规则、状态迁移、阈值语义、设备输入或设备输出时，必须同步更新该文件。

## 二、内容结构

`TESTING.md` 应按以下顺序编写：

1. 基本信息。
2. 整体玩法原则。
3. 观察项。
4. 公共准备。
5. 多个测试场景。

文档应保持简洁。不要复制完整需求、实现过程或源码说明；需要背景时链接到已有设计文档。

### 1. 基本信息

至少声明：

```markdown
- 游戏 ID：pressure-edging
- 游戏版本：1.2.0
- 所需设备：QIYA、TD01、DIANJI
- 测试方式：虚拟设备、实机输出观察
- 时间允许误差：正负 300ms
```

游戏 ID 和版本必须与 `index.html` 中的游戏 manifest 一致。没有定时行为时可以省略时间允许误差。

### 2. 整体玩法原则

玩法原则用于让人先确认“游戏整体应该怎样运行”。建议使用 `P1`、`P2` 等稳定编号，并控制在 5 至 10 条。

每条原则必须：

- 描述玩家或测试者能够感知的玩法规则。
- 明确输入、状态变化或输出之间的关系。
- 避免函数名、变量名和内部实现过程。
- 覆盖开始、正常流程、违规、恢复和结束；不适用的部分可以省略。

示例：

```markdown
## 整体玩法原则

- P1：正常状态下，刺激强度随时间逐步上升。
- P2：压力超过中间阈值后进入寸止；压力越高，刺激强度越低。
- P3：压力达到临界阈值时，刺激强度立即归零，并且只输出一次惩罚命令。
- P4：进入冷却后，压力必须持续低于中间阈值达到指定时间，游戏才能恢复。
- P5：游戏结束或手动停止后，所有设备输出必须归零。
```

如果玩法原则本身与产品预期不一致，应先修正文档或玩法设计，不能用场景测试通过代替玩法审查。

### 3. 观察项

只列出判断测试结果所需的输入和输出，例如：

```markdown
## 观察项

- 游戏状态：`Normal`、`Edging`、`Cooldown`
- 传感器输入：压力值
- 设备输出：电机强度、惩罚命令及其次数
- 用户反馈：页面警告、语音和日志
```

状态和输出必须可以通过页面、日志、调试状态或设备命令记录观察。设备输出应尽量写到逻辑设备、能力、动作和参数，例如 `punish.shock.start({ voltage: 24 })`，不能只写“设备正常响应”。

### 4. 公共准备

多个场景共用的设备映射、参数和初始值统一写在这里，避免每个场景重复。每个场景应能在重置公共状态后独立执行，不能依赖上一个场景遗留的状态。

```markdown
## 公共准备

- 参数：中间阈值 60，临界阈值 90，冷却时间 3 秒。
- 映射：QIYA 为 `sensor`，TD01 为 `motor`，DIANJI 为 `punish`。
- 每个场景开始前重新启动游戏并清空设备命令记录。
```

## 三、测试场景要求

每个场景只验证一个清晰的状态变化或边界行为，并必须包含以下字段：

```text
验证原则
当前状态
输入变化
预期状态
预期输出
违规条件
```

- **验证原则**：引用该场景覆盖的 `P1`、`P2` 等玩法原则。
- **当前状态**：写明状态、相关输入、计时和已有输出，不能只写状态名称。
- **输入变化**：给出明确数值、持续时间和操作顺序。
- **预期状态**：写明变化后的状态；状态不应变化时也要明确写出。
- **预期输出**：写明页面反馈和设备命令的动作、参数、次数；没有输出也是需要验证的结果。
- **违规条件**：列出应当警告的实际偏差，尤其是错误输出、重复输出和不应发生的输出。

示例：

```markdown
### T02：达到临界压力

- 验证原则：P2、P3
- 当前状态：`Edging`，压力 80，电机强度 20，尚未输出惩罚命令。
- 输入变化：将压力提高到临界值 90，并保持 1 秒。
- 预期状态：进入 `Cooldown`。
- 预期输出：电机强度归零；输出一次 `punish.shock.start`，后续循环不得重复输出。
- 违规条件：未进入冷却、强度未归零、未输出惩罚命令或输出超过一次。
```

### 场景覆盖范围

根据游戏实际玩法，测试场景至少覆盖：

- 正常流程中的主要状态变化。
- 阈值以下、等于阈值和阈值以上的边界行为。
- 违规成立与违规未成立，包括防抖或倒计时边界。
- 违规后的警告、设备输出和恢复流程。
- 游戏完成、手动停止后的最终输出。
- 可选设备缺失、输入停止或设备断线会改变玩法时的处理。

不适用于该游戏的场景不需要为了凑数量而编写。

## 四、虚拟设备与实机测试

虚拟设备和实机应执行相同编号、相同输入变化和相同预期结果的场景。只有操作方式不同时，才在场景中补充“虚拟设备操作”和“实机操作”。

- 虚拟设备测试通过属性修改或时间轴注入输入，并通过设备命令记录检查输出。
- 实机测试通过传感器或测试工具产生相同输入，只观察实际下行输出，不连接人体执行惩罚。
- 实机无法精确复现的输入，应写明允许范围，不能把“人工观察正常”作为通过标准。
- 虚拟设备与实机结果不一致时，分别记录两边的实际输入、实际输出和时间点。

## 五、结果与警告

所有预期都满足时，场景记为 `PASS`。任一实际状态或实际输出不符合文档时，Agent 必须输出 `WARN`，记录预期、实际和证据，然后在重置状态后继续执行其他独立场景。

统一格式：

```text
[WARN][pressure-edging][T02]
预期：进入 Cooldown，电机强度归零，并输出一次 punish.shock.start
实际：保持 Edging，输出了两次 punish.shock.start
证据：设备命令记录、页面状态或日志位置
```

以下情况也必须警告：

- `TESTING.md` 缺失，或者游戏 ID、版本与 manifest 不一致。
- 整体玩法原则互相矛盾，无法确定预期。
- 场景缺少必要初始值，无法稳定复现。
- 实际出现文档没有声明的设备输出。
- 因无法观察状态或输出而不能判断结果。

## 六、开发完成检查

提交游戏开发改动前确认：

- 游戏目录存在 `TESTING.md`。
- 整体玩法原则已经由人检查，且与当前产品预期一致。
- 每条关键玩法原则至少被一个测试场景覆盖。
- 每个场景都包含当前状态、输入变化、预期状态、预期输出和违规条件。
- 虚拟设备测试已经执行，所有警告均有结论。
- 需要实机验证时，已经完成实机输出观察并记录差异。
- 玩法或游戏版本变化已同步更新 `TESTING.md`。

# PC 客户端远程协助调试调研

日期：2026-09-04

范围：安装版 UnderSilicon（Electron）上，用户授权后让技术人员远程排障。只调研，不实现。

## 结论

能做，但不要做成真正的系统 SSH。

推荐：面板里做一个默认关闭的「远程协助」会话。用户点允许后，客户端主动连国内中继，技术员拿到限时通道。先做只读诊断（实时日志、设备/连接快照），再考虑白名单 API。不要开系统 shell，不要默认转发 CDP 或 `/bridge`。

现成的「远程」都不是这件事：远程投影/对战是控硬件；诊断上传是一次性日志包；本机 CDP/inspect 只在开发者电脑上有用。

## 现有能力

| 能力 | 现状 | 和远程排障的关系 |
| --- | --- | --- |
| 诊断日志上传 | 日志页按钮 → `api.undersilicon.cn/telemetry/log-bundles` | 事后看包，不能交互、不能复现 |
| 远程设备投影 / remote-play | 房间 MQTT，用户必须点允许 | 控的是设备，进不了用户电脑 |
| 账号 + admin telemetry | `https://undersilicon-admin.pages.dev/telemetry` | 可挂会话入口，没有实时通道 |
| 本机 CDP / Node inspect | 9224 / 5858；打包 exe 也可 `--remote-debugging-port` | 只监听本机；文档已写明生产不要常开 |
| 本机后端 | Electron 内 `127.0.0.1:5278`，`listen(port)` 未绑 host | 无认证。ADR 0001：本机可信；一旦出本机必须先鉴权 |
| 国内中继机 | `47.116.46.164` / `api.undersilicon.cn` | 用户出网可达，适合做反向中继 |

用户机器在家用 NAT/CGNAT 后，没有公网 IP，不能让技术员直连 22 或 5278。

## 技术员实际需要什么

常见排障顺序，不是「登录 Windows」：

1. 版本、匿名 id、最近日志
2. 设备在不在、连接类型（BLE / 串口 / MQTT）、broker/mDNS 是否起来
3. 让用户点几下，看实时日志
4. 偶发：打几个只读 API，或让客户端再打一份完整日志
5. 极少：看前端页面（CDP）、看文件、开系统命令行

1–4 就能覆盖大部分客服。5 成本高、隐私风险高，不该当 v1。

## 方案对比

### 不推荐当产品功能

**第三方远控**（向日葵 / ToDesk / TeamViewer / RustDesk）：用户会用，但不该打进安装包。成人硬件 + 桌面远控，隐私和品牌都差；杀软也爱报。人工兜底可以口头让用户开，不要集成。

**本机 OpenSSH Server**：Win10 是可选功能，要管理员、防火墙、sshd。装上等于整台电脑交给技术员。过重。

**Tailscale / Cloudflare Tunnel / VS Code Tunnels / ngrok**：国内家用网不稳定或要额外账号。VS Code Tunnels 还绑微软账号，不适合装进给用户的包。

**生产常开 CDP 再做端口转发**：CDP 能在渲染进程执行 JS，等于控制应用。文档已禁止默认常开。

### 能打通、但权限过大

**反向 SSH / frp / rathole**：用户侧主动连有公网 IP 的中继，把 `127.0.0.1:22` 或 `5278` 映出去。NAT 不是问题，国内也常用。

问题：5278 和 `/bridge` 现在无认证，映出去就能驱动设备。frp 二进制进安装包也容易被杀软当木马。若走这条，必须会话期临时开、只映白名单端口、中继侧再鉴权；仍不建议 v1 就映系统 SSH。

### 推荐：面板内「远程协助会话」

交互抄 remote-play：用户点允许 → 确认弹窗（可显示技术员身份）→ 倒计时 → 随时断开。断开即拆隧道。

通道：客户端出站 WSS/MQTT 连已有国内 API，不要求用户开端口、装 SSH、改路由器。

能力分层：

| 层 | 内容 | 建议 |
| --- | --- | --- |
| L1 只读 | 实时日志、设备列表、连接类型、MQTT/mDNS 状态、版本、匿名 id | v1 就做 |
| L2 诊断动作 | 再上传日志包、重连 broker、触发已有扫描 | 白名单 RPC，不要任意命令 |
| L3 本机 API | 会话 token 代理部分 `/api/*` | 先给远程调用加鉴权，重审 ADR 0001 |
| L4 深度 | CDP 或受限 PTY | 二次确认；PTY 只跑诊断 CLI，不要 `cmd.exe` |

中继三种接法：

1. **自建 WebSocket 中继**（最贴账号 JWT / admin 后台）。技术员走 `undersilicon-admin`，用户走面板。控制面和数据面都自己管。
2. **复用房间 MQTT**。同意、TTL、1v1 已经有。适合信令和小快照；实时日志流和交互式 shell 不合适。
3. **会话期内动态 rathole/frp**。技术员体验最像 SSH，运维和杀软成本最高。

优先 1。已有 Node 后端和国内机，不必再塞穿透二进制。

## 安全底线

- 默认关；用户显式允许才建连。不能静默常驻。
- 限时（建议 ≤ 1 小时）+ 界面倒计时 + 一键断开。断开后中继立刻作废 token。
- 禁止把 `/bridge` 和未鉴权的 5278 暴露到公网。ADR 0001 写明：多机/联网时 bridge 认证是第一优先级。
- 审计：谁发起、哪个匿名 id、何时连、何时断。可挂现有 telemetry。
- 实现用 Node 出站 WebSocket，不要在安装包里塞 frp。
- 协助过程不要默认能控电击/振动；若要测设备，走现有远程投影的钳制和停机，不要混进调试通道。

## 工作量（粗估）

- L1+L2：中。复用日志收集、匿名 id、账号、类似房间的同意流；云侧加会话表和 WSS 中继。
- L3：中偏大。必须先给远程 API 加会话鉴权，不能直接转发本机 HTTP。
- 真 SSH / 桌面远控 / 常开 CDP：大，且产品风险高，不值。

## 建议

先做 L1+L2，挂在设置或日志页的「允许远程协助」，技术员在现有 telemetry 后台点入会话。真 SSH 不值得做进面板。若以后一定要「像 SSH」，做白名单诊断 CLI，不要系统 shell。
